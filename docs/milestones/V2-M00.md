# V2-M0 — Requirements, decisions and owner preparation

**Tag:** none (documentation). **Model:** strongest available, high reasoning for S1–S2; smallest tier for S3. **Prerequisite:** V1 released (`v1.0.0`). Run before M1.

**Requirements:** all V2 requirements (`docs/v2-requirements.md`).

Goal: V2 enters the document system of V1. Every V2 requirement becomes an atomic entry in `docs/requirements.md` with an ID, target and milestone; decisions, limitations and the architecture description match; an independent review finds no contradictions; the owner starts the tasks that take weeks.

## Steps (the owner commits after each)

### S1 — Requirements and traceability

1. For every `R-xxx` (and `D-n` where it carries a testable fact) of `docs/v2-requirements.md` add atomic entries to `docs/requirements.md` in the V1 format `**TOPIC-nnn** [v2·todo·Mn] statement`. Use the existing topics (FIL, ORG, DET, ANN, SLD, NAV, SAV, UIX, I18, PLT, PIP, TST, NFR, GEN, ARC, PLY, STY). Add new topics only where none fits: `EDN` (editions and feature switches), `MRK` (marks, labels, bookmarks), `EXP` (export), `HNT` (first-run hints), `STO` (store publishing). IDs are never reused.
2. Mark V1 requirements that V2 changes as `changed` and keep the old text in `docs/changelog.md`. Known cases: PLY-002 (start at the start mark), ORG-014…ORG-024 (marks per system, tools instead of chips, labels), SAV-002…SAV-004 (new schema), STY-001…STY-004 (removed: pen and finger both draw), FIL-003/FIL-004 (file entry instead of tabs), FIL-008 (long press on "+"), SLD-013…SLD-015 (ratio start value), ANN-004/ANN-006 (thickness, undo for all tools), NAV-002 (modifier keys: Ctrl/Cmd+Z only), DET-013/DET-014 (parameter popup instead of levels). Check the list against the code and requirements; add what is missing.
3. Each entry names its milestone (M1…M19) from `docs/roadmap-v2.md`. A requirement belongs to exactly one milestone.
4. Write the map `R-xxx` → `TOPIC-nnn` as a table at the end of `docs/changelog.md` (section "V2 requirement map").
5. Update `docs/limitations.md`: BKL-006, 007, 010, 012, 016, 017, 019 → promoted to V2; BKL-023 → dropped (LIM-016 stays); BKL-008, 013 and shortcuts beyond undo/redo (#55) → backlog for V3; LIM-006 (no box editing), LIM-018 (no undo for marks), LIM-025/030 (text/stamps) → lifted by V2.

### S2 — Decisions, architecture, review

1. `docs/decisions.md`: one `DEC-nnn` per decision D-1…D-32 of the V2 requirements that is not already a requirement (file identity by name, marks on systems, persistence behind switches, tag scheme `v1.<n>.0`, Bravura as the stamp font). Add the Bravura dependency here (name, version, license SIL OFL, reason).
2. `docs/architecture.md`: (a) marks belong to systems (data model, junction derivation for `core/` playing order); (b) the edition-configuration layer: two feature files in `config/`, how a feature reads its switch, how the build selects the file; (c) the cross-file reference (file name + page + system) and where it is stored; (d) the new ports needed (share-in, file-list persistence switch). Keep the import matrix intact or state the change.
3. Review (read-only, fresh session, as `V1-M0c`): check atomic, non-conflicting, precise, complete (every ID in exactly one milestone), implementable, consistent numbers. Output `docs/review-report.md`. Fix findings in the documents (not in code).
4. `docs/README.md` index and `docs/roadmap-v2.md` stay consistent with the result.

### S3 — Update AGENTS.md and sync its copies

The owner authorizes this milestone (and only this one, for this change) to edit `AGENTS.md`.

1. Edit **only `AGENTS.md`**, then run `npm run sync:agents` so `CLAUDE.md`, `.claude/CLAUDE.md` and `.gemini/GEMINI.md` become identical copies. Never edit the copies by hand.
2. Allowed changes, nothing else:
   - "Read in this order" and "Layout of the documents": add `docs/roadmap-v2.md` and `docs/milestones/V2-Mnn.md` next to the V1 entries (V1 files stay, they are history).
   - "Naming and versions": V2 milestones `V2-M<n>` → tag `v1.<n>.0`; the release of V2 additionally tags the last milestone's commit `v2.0.0` (annotated); until then fixes to V1 are patch-only (`v1.0.p`) (collision rule in `docs/roadmap-v2.md`); the owner tags, the agent never does.
   - "Workflow": "one fresh session per milestone" applies to V2 milestones too.
   - "Git: the owner commits and pushes": one added bullet, "Never use the GitHub CLI (`gh`) or any GitHub API, not even read-only (PRs, issues, CI status, releases). The owner does all GitHub work. This replaces the narrower `gh pr …` ban.", and the existing `gh pr …` mention in the bullet that forbids pull requests points to it (owner decision, S2 review).
   - "Standing rules": one added line that new features carry a feature switch (`docs/roadmap-v2.md`, "Rules that hold in every V2 milestone"), if the owner's review of the diff agrees.
3. **Apart from the one Git bullet above, the "Git: the owner commits and pushes" section and all other rules stay untouched.** Editing `AGENTS.md` does not allow committing, staging, branching or tagging.
4. Run `npm run lint` (the agent-copy check must pass) and show the diff of `AGENTS.md` in the step summary for the owner's review.

## Do not

- Do not change source code, tests, `tunables.ts` or workflows.
- Do not edit `CLAUDE.md`, `.claude/CLAUDE.md` or `.gemini/GEMINI.md` by hand (only through `npm run sync:agents`), and do not edit `AGENTS.md` beyond the changes listed in S3.
- Do not renumber existing IDs; do not reuse IDs.
- Do not write milestone steps into requirements.

## Acceptance criteria

- [ ] Every V2 requirement exists in `requirements.md` with `v2` target, status and exactly one milestone.
- [ ] Changed V1 requirements are marked `changed`, and `changelog.md` holds old text and the R-map.
- [ ] `limitations.md`, `decisions.md`, `architecture.md` updated; Bravura recorded.
- [ ] `docs/review-report.md` exists and all findings are fixed or listed as questions.
- [ ] `npm run lint` passes (traceability check accepts `v2·todo` entries).
- [ ] `AGENTS.md` updated as listed in S3 (only the one Git bullet added), the three copies synced, `npm run lint` green.

## Owner step

Review the diff (check the `AGENTS.md` change and that all four copies are identical), commit all four files together (no tag), and start the owner tasks above.
