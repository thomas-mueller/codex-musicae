# V1-M4 — Contracts and tests

**Tag at the end:** `v0.4.0`. **Model:** strongest available, high reasoning (the tests check every later step). **Prerequisite:** M1 done.

**Requirements:** ARC-005, TST-001 (and the test scaffolding for DET-005…011, DET-024, PLY-001…013, SLD-001…006, SLD-012, SLD-013, SLD-014, SAV-007, NFR-006).

Goal: put the verified contracts and fixtures into `src/`, write the unit tests from them, and prove that all tests fail for exactly one reason: `not implemented`. No implementation.

Inputs (read `docs/contracts/README.md` first): `docs/contracts/core/*.ts`, `docs/contracts/core/fixtures/*.cases.ts`, `docs/contracts/ports/*.ts`.

## Steps (the owner commits after each)

### S1 — Copy the contracts

1. Copy to `src/app/core/` only the **first-set** files: `model.ts`, `geometry.ts`, `system-selection.ts`, `detection.ts`, `junctions.ts`, `aspect-ratio.ts`, `playing-order.ts`, `slides.ts` and the fixtures `geometry`, `detection`, `junctions`, `aspect-ratio`, `playing-order`, `slides` (`*.cases.ts`) into `src/app/core/fixtures/`; write a `core/index.ts` that exports exactly those modules. `junctions.ts` and `slides.ts` are copied complete: they also contain the later function `findEntryForSystem` (M12) as a stub; they get no spec now and stay `not implemented` until those milestones. Copy `docs/contracts/ports/` to `src/app/ports/`. All other contract files (`lru-cache`, `scheduler`, `view`, `layout`, …) are copied by the milestone that needs them (see `docs/contracts/README.md`). Keep file names and exports; keep the doc comments (they contain the algorithms).
2. Adapt only what the project setup forces: formatting, lint complaints that do not change signatures. The `ports/` layer may import `@angular/core` for `InjectionToken` and `Signal` (check the M1 boundary config allows exactly that and adjust the lint rule if needed).
3. `npm run lint` and the TypeScript build must pass. Stubs keep `throw new Error('not implemented')`.

### S2 — Write the tests

One spec file per topic next to the code: `geometry.spec.ts`, `detection.spec.ts`, `junctions.spec.ts`, `aspect-ratio.spec.ts`, `playing-order.spec.ts`, `slides.spec.ts` in `src/app/core/`, plus `src/app/ports/result.spec.ts`.

- Table-driven: for every fixture group, ``it(`${c.req} ${c.id}: ${c.name}`, …)`` (use `c.id` when there is no `name`). Use `toEqual` for exact data and a small helper `expectCloseDeep(actual, expected)` (recursive, numbers with `toBeCloseTo(expected, 9)`) for anything containing floating-point numbers.
- `pageTransformCases` test both directions (`userToDisplay` and `displayToUser`).
- `forcedBreaksCases`: `forcedBreaks(generatePlayingOrder(case.input), new Set(case.breaks))`.
- `systemNumbersCases`: `systemNumbers(generatePlayingOrder(case.input), case.input.systemCount)`.
- `barsOfJunctionCases`: use the bars of case `J1`.
- `slideIndexOfEntryCases`: use the slides of case `SP02` (`packSlidesCases`).
- `result.spec.ts`: `ok(1)` is `{ ok: true, value: 1 }`; `err('x')` has no `detail` key; `err('x', 'why')` carries it (ARC-005).

Add these extra tests (names contain the ID in brackets):

| Test | ID |
|---|---|
| For every rotation and 20 deterministic points (fixed list, no randomness): `displayToUser(userToDisplay(p)) ≈ p` | SAV-007 |
| `selectSystems` does not modify its input array or its components | DET-005 |
| `generatePlayingOrder` invariants over all fixture inputs: every entry in 1..N; `between.length === max(0, entries.length - 1)`; `between[i][0] === entries[i]`; calling twice gives equal results | PLY-002 |
| `generatePlayingOrder` for N = 2000 with no jumps returns 2000 entries in under 100 ms | NFR-001 |
| `packSlides`: slide entry ranges cover `0..entries.length-1` without gaps or overlap for every fixture case | SLD-003 |
| `packSlides`: every non-enlarged slide has `stackHeight <= height + 1e-9` | SLD-003 |
| `stepAspectRatio` repeated from 1.78 downwards ends at exactly 0.5 and never leaves [0.5, 2.0] | SLD-013 |

You may add further edge cases you find; each must have a clear expected value derivable from the contract text.

### S3 — Prove the tests are red for the right reason

1. Run the unit tests. Expected: every test fails, and every failure message contains `not implemented`. Tests that fail with a type error, import error or wrong expectation are defects of the test: fix the test.
2. The only tests allowed to pass: those that do not call a stub (`result.spec.ts`, helper tests).
3. Put the counts (tests, failing, passing) into your suggested commit message for the owner.

### S4 — Independent re-derivation

The fixtures were produced by a reference implementation. Check them without running code:

1. For each fixture group pick the five most complex cases (for playing order: O03, O04, O06, O11, O17; for slides: SP02, SP03, SP05, SP06, SP10; for detection: D06, D07, D09, D11, D13; for junctions: J1, J2).
2. Derive the expected value by hand from the contract's doc comment only, then compare with the fixture.
3. Write every mismatch, ambiguity or untestable statement to `docs/questions.md` with your derivation. **Do not edit fixtures or contracts.** If there are no findings, write "no findings" there.

## Do not

- Do not implement any function body; do not change signatures or expected values.
- Do not add dependencies beyond the test tooling from M1.
- Do not touch `state/`, `features/` or adapters.
- Do not delete the doc comments in the stubs.

- [x] All spec files exist; the unit test run shows only `not implemented` failures plus the allowed passing tests.
- [x] Every test name contains a requirement ID.
- [x] `docs/questions.md` contains the re-derivation result.
- [x] Requirement statuses: ARC-005 and TST-001 are `done`; the others stay `todo`.
