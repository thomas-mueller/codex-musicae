# V2-M7 — Undo and redo for all tools

**Tag at the end:** `v1.7.0`. **Model:** mid-tier, medium effort. **Prerequisite:** M4, M5 done.

**Requirements:** R-55a (and its `TOPIC-nnn`).

**Requirement IDs:** ANN-014, ANN-015, ANN-016, ANN-017, NAV-021, NAV-022.

Goal: undo and redo cover every editing tool in both modes, with a separate history per mode and keyboard shortcuts. V1 covers strokes only (ANN-006, up to `T:annotation.undoDepth` = 200 steps, annotation mode, no modifier keys).

## Design

- An **edit history** per document and per mode (`annotation`, `organization`) in `state/`. An entry is a command object with `do` and `undo` that works on the stores (strokes, marks, systems), not on the pixels.
- Annotation history: strokes added/erased (V1 behavior), later text, stamps and moves (M11/M12 register their commands).
- Organization history: marks added/removed/edited (M4 model), systems added/deleted/replaced (M9), page rerun results (M8). A system deletion command stores the deleted marks so undo restores them (D-24).
- Depth `T:annotation.undoDepth` for both histories (rename the tunable to `history.depth` only if the V1 tests allow; otherwise keep the name and add the alias).
- History is cleared when the document closes (V1), and a history entry never survives a page rerun that invalidates its systems (the entry is dropped; no half-restores).

## Steps (the owner commits after each)

### S1 — History core (`core/`, pure)

`core/history.ts`: a generic bounded undo/redo stack (`push`, `undo`, `redo`, `clear`, `canUndo`, `canRedo`, redo cleared on push). Fixture-driven spec (depth limit, redo invalidation, interleaving, empty stack, `clear`).

### S2 — Store integration

1. `state/`: `EditHistoryStore` with one history per mode; the V1 stroke undo code is moved onto it (behavior unchanged; V1 tests for ANN-006 must stay green unchanged).
2. Commands for marks (M4 API: `addMark`, `removeMark`) so that M10 only calls the store; a command for "delete system" prepared for M9 (stub with tests using the M4 deletion rules).
3. Buttons: undo/redo in annotation mode (V1 position) **and** in organization mode (same icons `T:icons.undo`, `redo`), disabled when the stack is empty.

### S3 — Keyboard (R-55a)

1. `input/`: Ctrl/Cmd+Z → undo, Ctrl/Cmd+Shift+Z → redo in annotation and organization mode; platform detection in `input/` (Cmd on macOS/iOS, Ctrl elsewhere); key bindings in `T:keys`. V1 ignores Ctrl/Alt/Meta combinations (NAV-002): that rule is relaxed for these two bindings only; every other modified key stays ignored. The change to NAV-002's tests is **explicitly allowed** and limited to these two combinations.
2. Not active in slide mode or in the settings mode; ignored while a text field has focus.
3. No other shortcut is added (V3).

## Tests

- Unit: history core; stroke undo parity with V1; mark add/remove undo; system deletion undo restores marks; key mapping per platform; ignored contexts.
- E2E (Chromium, WebKit): draw, undo, redo with buttons and keys in annotation mode; add a jump (through the V1 chip UI until M10), undo, redo; mode histories are independent.

## Do not

- Do not add tools or UI for marks/systems (M9, M10).
- Do not add other keyboard shortcuts.
- Do not change stroke storage or the eraser.

## Acceptance criteria

- [ ] Both histories exist, bounded, cleared on close; V1 ANN-006 tests green and unchanged.
- [ ] Buttons and keys work in both modes; key tests green on macOS-style and other mappings.
- [ ] Requirement statuses updated; lint, unit tests, E2E smoke, build green.
