# V2-M2b — Large scans on 4K displays

**Tag at the end:** `v1.2.1`. **Model:** mid-tier, medium effort. **Prerequisite:** V2-M2 done and tagged `v1.2.0` (the real-PDF corpus, the working raster of NFR-025 and the `perf` project exist).

**Requirements:** DEC-148 (reason and numbers), NFR-025 (context), NFR-004, NFR-005, NFR-006, NFR-010, NFR-020.

**Requirement IDs:** NFR-026, NFR-027, TST-022.

Goal: changing slides on a scan with large images stays fast on 4K displays (3840×2160 physical pixels, any `devicePixelRatio` up to the cap), in annotation and in presentation mode, without lowering the render resolution.

## Background (read DEC-148 first; do not reopen it)

- Slides are cut from a whole-page working raster (`WorkingResolutionRenderer`, NFR-025) only while the requested scale is at most the working scale. The raster is capped by `T:resources.maxCanvasPixels` (12 MP), about 4.9 pixels per point for an A4 page. A full-width slide on a 4K stage needs about 6. Then **every** slide change is a direct region render of pdf.js (`renderFromSource`), one at a time.
- `PdfJsDocumentHandle.renderRegion` ends every render with `page.cleanup()`. In pdf.js this clears the parsed page content and the decoded images (`_intentStates.clear(); objs.clear()`), so two slides of one page decode the scan twice.
- A 4K slide bitmap is about 33 MB. The cache budget is 96 MB on a 2 GB device and 192 MB on 4 GB (`T:resources.cacheBudgetByDeviceMemoryGb`); the current slide plus two prefetched neighbors can exceed it, so a prefetch may evict the slide on screen.
- A larger or banded whole-page raster is rejected (DEC-148). Do not touch `workingLongSidePx`, `renderWorkingRaster` or detection.

Existing from the analysis chat (uncommitted or committed by the owner before this milestone): `e2e/perf/render-profile.spec.ts` (report-only profile: two tests for the regular and largest PDF, plus the annotation/presentation comparison at 1920×1080, ratio 2) and the counter `directRenders` next to `sourceRenders` in `WorkingResolutionRenderer.stats`, exposed by the development debug hook (`__cm.directRenders()`). This milestone extends them; run `git status` first and report what is already in the tree.

## Steps (the owner commits after each)

### S1 — Baseline at 4K (TST-022)

1. Extend `e2e/perf/render-profile.spec.ts`: the mode comparison runs at three viewports, `3840×2160` ratio 1, `2560×1440` ratio 1.5 and `1920×1080` ratio 2 (constants named once, no inline numbers), in annotation and presentation mode, on the regular real PDF with the most pages. Per run it reports: slide canvas size (CSS and device pixels), `sourceRenders` split into raster builds (`sourceRenders − directRenders`) and `directRenders`, key-to-repaint (median, 95th percentile) for at least 15 slide changes of which each is waited for until repainted (poll the canvas repaint, not a fixed wait; the first version missed most changes with a fixed 1.5 s wait), JS heap after garbage collection and `__cm.cache.totalBytes` against `budgetBytes`.
2. Test names carry `TST-022 NFR-027`. The spec asserts only that it measured something.
3. Run it and put the numbers in the report as the **baseline** (this is the "before" of S2 and S3). If the presentation run still shows a 300×150 canvas, the wait for the first paint is wrong: fix the test, not the app.

### S2 — Keep pdf.js page state warm (NFR-026)

1. Tunables (`src/config/tunables.ts`, `pdf` section, every number with a comment): `warmPagesByDeviceMemoryGb` with starting values `{ 1: 1, 2: 1, 4: 2, 8: 3 }` and `warmPagesDefault: 2` (unit: pages). Resolve them with the existing `cacheBudgetFor` (`src/app/core/cache-budget.ts`, generic over the bucket table; do not copy it).
2. In `PdfJsDocumentHandle` (`src/app/adapters/pdfjs/pdfjs-renderer.ts`): `renderRegion` no longer calls `page.cleanup()`. It records the page in a small LRU of page numbers; when a page leaves the LRU it is fetched with `getPage` and cleaned up; `destroy` cleans up all. `getPageInfo` keeps its `cleanup()` only if the page is not in the LRU. Cancelled or failed renders do not enter the LRU. The count comes in through the constructor options (like `createCanvas`), read from the device-info port in `app.config.ts`, so the adapter does not read the device itself.
3. Tab inactivity (NFR-020, V2-M6) is not built yet: leave a documented hook (`releaseWarmPages()` on the handle) and call it from the same place that drops the bitmaps of an inactive tab if that code exists; otherwise note in the report that M6 must call it.
4. Unit tests with the fake page (`PdfjsPage.cleanup` counted), names with `NFR-026`: no cleanup after a render while the page is warm; the page that falls out of the LRU is cleaned up; `destroy` cleans all; the LRU size follows the memory bucket; a cancelled render is not kept warm.
5. Run the profile of S1 again: report **before and after** (median and p95 key-to-repaint from the second slide of each page on, `directRenders`, JS heap, cache bytes). If the warm state shows no gain, stop and write the numbers to `docs/questions.md`; do not add other optimizations.

### S3 — The current slide survives its neighbors (NFR-027)

1. Measure first, in the profile at the three 4K viewports with a forced low budget (use `__cm.cache.budgetBytes` for the real bucket; for the 2 GB and 4 GB buckets set the budget in a unit test of the policy, not by faking `deviceMemory` in the browser): does prefetching a neighbor evict the displayed slide?
2. If yes: `ResourceGovernor.prefetchNeighbors` (`src/app/state/resource-governor.ts`) takes the estimated bytes of one slide bitmap and the cache budget into account: a pure function in `core/` (`prefetchCountFor(slideBytes, budgetBytes, wanted)`, deterministic, unit-tested with `NFR-027` in the names) returns the largest number of neighbors per side (0 … `T:resources.prefetchNeighbors`) for which the current slide and its neighbors fit with the margin `T:resources.prefetchBudgetShare` (fraction of the budget, a new tunable with a comment). `SlideView.prefetch` uses it. The render resolution is lowered only after prefetch is already 0 (existing order of NFR-010).
3. If no eviction occurs in the measurements, write that into the report and keep only the unit-tested function if it is needed by the warm-page numbers; do not add code that is not needed.
4. The slide canvas never exceeds `T:resources.maxCanvasPixels` at 3840×2160 (about 8.3 MP): assert it in the profile run (this is an assertion, not a speed budget).

### S4 — Documentation and report

## Tests

- Unit (Vitest): the warm-page LRU and cleanup (S2), the prefetch count function (S3), the tunable table lookup. All names contain the requirement ID.
- E2E (`perf` project, Chromium only): the profile of TST-022 (report only).
- No existing test is edited. The existing `NFR-025` unit tests of `working-resolution-renderer.spec.ts` and the existing `pdfjs-renderer` tests must still pass unchanged; if one fails because `cleanup()` is no longer called after a render, report it instead of editing it.

## Do not

- Do not change `workingLongSidePx`, `workingPagesKept`, the working raster, detection or the render scale, and do not lower the render resolution.
- Do not add dependencies, a worker, a band raster or a new cache.
- Do not add a feature switch: this is a performance change inside existing code with tunables (record in the report that the rule "new features carry a switch" was considered and does not apply).
- Do not set or change `T:budgets` values; do not edit other tests to make code pass.
- Do not touch layers outside `adapters/pdfjs`, `state/` (governor, slide prefetch call), `core/` (the pure function), `config/` and `app.config.ts`.
