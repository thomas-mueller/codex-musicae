# V2-M3b — Corpus suites: detection counts and load tests

**Tag at the end:** `v1.3.1`. **Model:** mid-tier, medium effort. **Prerequisite:** V2-M3 done and tagged `v1.3.0` (the real-PDF corpus of M2, the `perf` project and the budgets of M1/M2 exist). The owner has answered the two questions of S1 step 4 (Firefox difference, WebKit stall) in `docs/questions.md` before S2 starts.

**Requirements:** DEC-152 (reason and design), TST-002, TST-008, TST-015, DET-013, DET-035, NFR-025, NFR-028 (context).

**Requirement IDs:** TST-023, TST-024, TST-025, TST-026, TST-027.

Goal: every corpus PDF is used for what it is good for, and no more. The majority of the PDFs only check **how many systems the detection finds per page**. A few special PDFs (very long, very high resolution, hard to detect) only check that **the app stays correct and responsive** while detection and navigation run at the same time, and that its use of memory and CPU stays within the budgets. The detection numbers must survive a change of the detection algorithm or its settings (M8) without rewriting the corpus.

## Background (read DEC-152 first; do not reopen it)

- Today an entry in `e2e/corpus/expected.json` carries `level`, `systemsPerPage`, `knownLimitation` and, for files above 100 pages, `stress`. `detection-corpus.spec.ts` runs **all three levels** (`fast`, `standard`, `fine`; three full detection runs per entry) and asserts only the level named in the entry; the other two are printed. `detection-engines.spec.ts` runs every non-stress entry again on Chromium, Firefox and WebKit (two more runs). One WebKit job therefore runs about five full detection runs per entry with one worker, which is the suspected reason for the job taking up to 1 h 30 (to be measured in S1).
- Two open findings in `docs/questions.md` belong here: "V2-M02 — Firefox finds 14 systems on page 2 of the Bassoon part" (engine-dependent working raster) and "V2-M03 — WebKit corpus run is not deterministic on the large tiff2pdf scan" (blank raster under CPU load). **This milestone does not fix either in the app** (detection and rendering are out of scope); it makes the tests able to express them.
- The performance tests (`e2e/perf/budgets.spec.ts`, `render-profile.spec.ts`) pick their PDFs automatically (`pickPerfPdfs`: largest, regular, heavy). The numbers in `T:budgets` are the owner's; this milestone adds **no** timing budget.
- M8 replaces the detection `level` by a parameter set and adds detection settings the owner will vary. A change of algorithm must mean "add or change a profile", not "re-review the corpus".

## Design in short

1. **Suites.** Each entry says which suite(s) it belongs to: `detection` (systems per page are compared with the owner's expectation) and/or `load` (heavy computation and navigation in parallel, responsiveness and resources). A file can be in both. Most are `detection` only; the special files are `load` only or both. Optional `tags` (`scan`, `high-dpi`, `long`, `skewed`, `faint`, …) describe why a file is there; they select nothing by themselves, except that the helper proposes the suite from the page count.
2. **Expectations are the true counts.** `systemsPerPage` is what the owner has reviewed as correct, independent of any algorithm. What a particular profile or engine gets **differently** is recorded in `deviations`, and the spec asserts the deviating numbers exactly so that a change is noticed (this replaces `knownLimitation`).
3. **Profiles.** A profile is a named way to run detection (today: the V1 levels; from M8: parameter sets). The list is `e2e/corpus/profiles.json`. Exactly one function in `e2e/support/corpus.ts` (`runProfile`) turns a profile into the call of the debug hook; M8 changes that function and the file, nothing else.
4. **Load suite** applies the existing budgets of `T:budgets` to more files and more simultaneous actions, plus invariants through the debug hook (bitmap cache bytes, canvas pixels). It fails the `perf` job on a breach; it reports its numbers in the job summary.

### Entry format (V2)

```json
{
  "file": "IMSLP35620-PMLP01586-Beethoven-Op067.Bassoon.pdf",
  "source": "url",
  "suites": ["detection"],
  "tags": ["scan"],
  "profiles": [],
  "engines": ["chromium", "firefox", "webkit"],
  "systemsPerPage": [14, 15, 15],
  "deviations": [
    { "profile": "v1-standard", "engine": "firefox", "systemsPerPage": [14, 14, 15], "note": "…" }
  ],
  "pages": 3,
  "note": "",
  "reviewed": true
}
```

- `suites`: non-empty, values `detection` | `load`. `systemsPerPage` is required for `detection` and empty for a `load`-only entry (the helper records only `pages`).
- `profiles`: extra profiles this entry is asserted under, on top of the profiles marked `"default": true` in `profiles.json` (an entry for a special detection setting names it here).
- `engines` (optional, default all three desktop engines): where the `detection` suite runs this entry. Narrowing it is the owner's decision and needs a `note` (for example the WebKit memory of a very large scan).
- `deviations`: `profile` (a name from `profiles.json`), optional `engine`, the exact `systemsPerPage` that run gives, a `note`. A run that matches a deviation asserts those numbers; every other run asserts `systemsPerPage`.
- `level`, `knownLimitation` and `stress` are gone: `level` becomes the default profile, a limitation becomes a deviation, a stress file becomes `suites: ["load"]`.

2. **Schema.** `scripts/lib/corpus-schema.mjs` (pure, no dependency): `validateEntry(entry, profiles)` returns the list of problems (unknown suite or profile or engine, `detection` without counts, `load`-only with counts, a `deviation` that names an unknown profile, an `engines` narrowing without a `note`, `reviewed` missing on an entry that has counts). `scripts/lib/corpus-files.mjs` gains `entriesOf(entries, suite)` and keeps `resolveCorpusEntry`. `STRESS_MIN_PAGES` stays: the helper proposes `["load"]` for a file above it and `["detection"]` otherwise (the owner may add the other suite).

4. **Migrate `expected.json` once** with a throw-away script (not committed): `level` dropped (it is the default profile), `stress: true` → `suites: ["load"]`, everything else `suites: ["detection"]`, `knownLimitation` (all `null` today) dropped, `engines` and `deviations` empty. ### S2 — The detection suite (TST-024, TST-027)

1. **One spec.** `e2e/detection-corpus.spec.ts` becomes the only detection spec: for every reviewed entry of the `detection` suite, for every engine in its `engines` that is the current project, for every profile (the defaults plus the entry's own): **one** detection run through `runProfile`, then `expect(counts).toEqual(expected)` where `expected` is the matching `deviations` entry if there is one, else `systemsPerPage`. `detection-engines.spec.ts` is removed (`git rm`): its assertion (the same counts in every engine) is this loop on all three engines. The test title keeps `TST-002 TST-015 DET-013 DET-035 NFR-025` so that traceability does not lose its tests, and adds `TST-024`.
2. Draft entries (`reviewed: false`) and entries whose file is absent are skipped with a visible reason, as today. The `smokeEntries` rule (first three entries on Firefox and WebKit) is dropped: the owner narrows `engines` where needed. The per-entry output prints the table of counts that the run produced (information, as today).
3. **Apply the owner's answers of S1 step 5.** The Firefox difference on the Bassoon part is not recorded (left for M8); apply the answer on the WebKit entry; do not edit counts of other entries.
4. **Time caps (TST-027).** Test timeout per entry = base + one scaled run (`detectionRunTimeoutMs`), not one per level. Set `timeout-minutes` of each e2e engine job in `.github/workflows/e2e.yml` to twice the measured time of S1 (rounded up to 5 minutes; the numbers go in the report), keep `workers: '1'` for WebKit. A detection run that does not finish fails its test with the engine and entry in the message (the test timeout), never the whole job by timeout alone.
5. **Helper** (`scripts/lib/make-expected.mjs`, `e2e/tools/propose-expected.spec.ts`): proposes entries in the V2 format (suite from the page count, default profile, `reviewed: false`); it never overwrites a reviewed entry without `--force` and keeps its `suites`, `tags`, `engines` and `deviations` when it does. The same `validateEntry` runs on the proposal.

Tests: `TST-024` unit tests of the expectation choice (`expectedFor(entry, profile, engine)`: a matching deviation wins, otherwise the counts; a deviation for another engine or profile is ignored) as a pure function in `scripts/lib/corpus-files.mjs`; of the helper's suite proposal; of "never overwrite reviewed". E2E: the detection spec itself on Chromium, Firefox and WebKit.

### S3 — The load suite (TST-025)

1. **Select by suite.** `e2e/perf/support.ts` takes its PDFs from the `load` suite (`pickPerfPdfs` keeps its rules for `largest`, `regular` and `heavy`, applied to `load` entries; a `detection`-only entry is no longer a perf file). If the `load` suite is empty the perf specs skip with a reason, as today.
2. **Scenarios** (new `e2e/perf/load.spec.ts`; reuse the helpers of `budgets.spec.ts` and `render-profile.spec.ts`: do not copy them). For **every** `load` entry, on Chromium, no retries:
   - `open`: open until the first slide is drawn (`T:budgets.openToFirstSlideMs`).
   - `parallel`: start detection of the whole file and, while it runs, drive the app: slide stepping, large jumps, scrolling, zoom in and out, and one pen stroke. Assertions: (i) after each action the **requested** page is the one displayed and its visible area is drawn (`displayedShare`, existing `DISPLAYED_SHARE`; a jump that is overtaken by the next one is not asserted), never a blank or a wrong page; (ii) slide change p95 within `slideChangeP95Ms`; (iii) the longest main-thread task within `drawingMaxLongTaskMs`; (iv) the stroke's added latency within `drawingMaxAddedLatencyMs`.
   - `resources`: sampled during `parallel` through the development hook: the bitmap cache never above its budget (`__cm.cache.totalBytes` ≤ `budgetBytes`), no canvas above `T:resources.maxCanvasPixels`, the JS heap at the end within `maxJsHeapMb`, never more than `T:resources.schedulerMaxPerClass` running tasks per priority class. A missing hook value is added to the hook (development build only), not guessed.
   - `throttled`: `parallel` again with `throttleCpu(CPU_THROTTLE)`, shortened to the first `IMPACT_SLIDE_CHANGES` slide changes. Assert **correctness and the resource invariants only** (i and the `resources` rules); timing is reported, not asserted (no new numbers).
3. All limits go through `budget()` of `e2e/perf/support.ts` (so `T:budgets.ciToleranceFactor` applies on CI). Do not change values in `T:budgets`; where a measurement shows a budget is too tight or too loose, **propose** the number in the report.
4. Firefox and WebKit run no load scenario. They keep their detection run (S2); a short "opens and displays" check on each is already part of `@smoke`.

Tests: `TST-025` in the title of every scenario. Unit: the pure part of the displayed-page check and of the invariants (`core`-free helpers in `e2e/perf/` are tested only if they are pure; otherwise the E2E run is the test).
