# V2-M9 — Refinement of detected systems

**Tag at the end:** `v1.9.0`. **Model:** mid-tier, medium effort. **Prerequisite:** M7, M8 done.

**Requirements:** R-36a…i, R-19b (refine and delete tools), D-24.

**Requirement IDs:** ORG-034, ORG-035, ORG-036, ORG-037, ORG-038, ORG-039, ORG-040, ORG-041.

Goal: the user can correct detection by hand: draw a rectangle that becomes a system box, optionally snapped to the detected content, and delete any system. V1 has no box editing (LIM-006).

## Steps (the owner commits after each)

### S1 — Core: box editing (`core/`)

1. `core/boxes.ts` (contracts and fixtures first): `insertSystem(page, boxes, rect)` puts the new box at the right position of the page's reading-order list (top-to-bottom, then left-to-right); `removeSystem`; `hintBox(rect, components)` = the largest combined bounding box of the detected component boxes lying inside the rectangle, or `null` when none. At least 25 fixture cases (overlap, rectangle partly outside the page, rectangle with no component, many components, equal tops).
2. Renumbering: system numbers on the page and global system indices follow the list; M4 deletion rules decide which marks are removed or kept.

### S2 — Tools and interaction (R-36a…d, R-36h/i)

1. **Refine tool** in the organization tool strip (R-19b): drawing creates a resizable rectangle (corners and edges); confirming it (tap outside or the confirm icon) saves it. A **long click** opens a popup with one boolean: (a) save the rectangle as the new system box, (b) **hint mode**: replace the rectangle by `hintBox`; if hint mode finds nothing the drawn rectangle is accepted without a message (R-36h).
2. **Delete tool**: a click on any system deletes it. Move and split work through delete plus redraw. No separate move or split tool.
3. Refinement only works on pages whose detection has finished (R-36i); on others the tools are disabled for that page (no message, only the existing provisional look).
4. Active areas for the tools are the whole system (no end zones; those belong to mark tools, M10).
5. Both operations are undoable commands in the organization history (M7); deleting a system deletes the marks stored on it, undo restores them.

### S3 — Persistence and consistency

1. Edited systems are written with the metadata (M4 schema) and marked as user-edited so that "rerun all pages" asks before replacing them (the V1 confirmation of DET-014 applies; text via translation keys).
2. A rerun of one page (M8) discards user edits on that page (documented behavior, covered by the confirmation of S3.1).

## Tests

- Unit: fixtures of S1; command do/undo; edited-flag persistence; tool state machine (long click popup, hint mode with and without components).
- E2E (Chromium, WebKit, a tablet profile): draw a rectangle on a corpus page, hint mode snaps, fallback accepts the rectangle, delete a system with a mark (mark removed; undo restores both), edit survives save and reload.

## Do not

- Do not add a move or split tool, resize handles for existing boxes, or a freeform shape.
- Do not change detection results of untouched pages.
- Do not change the mark tools (M10).

## Acceptance criteria

- [ ] Rectangle, hint mode, delete work; all undoable.
- [ ] Marks follow the D-24 rule; undo restores.
- [ ] Edits persist and are protected by the rerun confirmation.
- [ ] Requirement statuses updated; lint, unit tests, E2E, build green.
