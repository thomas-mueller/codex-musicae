**Tag at the end:** `v1.4.0`. **Model:** **strongest, high reasoning** for S1 (contracts, fixtures, independent re-derivation); mid-tier, medium for S2–S3. **Prerequisite:** M3 done.

**Requirements:** D-10, D-11, D-12, D-13, D-24, D-26, D-31, R-28k, R-30a, R-30e (and their `TOPIC-nnn`).

**Requirement IDs:** SAV-015, SAV-016, SAV-017, PLY-014, PLY-015, PLY-016, MRK-001, MRK-002, MRK-003, MRK-004, MRK-005, MRK-006, MRK-007, MRK-008, MRK-009, MRK-010, MRK-011, MRK-012, MRK-013, MRK-014, MRK-015.

Goal: marks belong to systems instead of the gaps between them. Storage, playing order and labels follow the V2 rules; existing V1 files keep opening through a migration. This milestone is `core/` and the metadata schema only: no UI.

## The model (normative)

- A **mark** is stored on one **system** and one **side**: left side (start of the system): `start`, `jumpTarget`, `bookmark`; right side: `jumpStart`, `stop`, `slideBreak`.
- A **jump** pairs a `jumpStart` and a `jumpTarget` and has a pass number ≥ 1 (V1 default: number of existing jumps from the same start + 1). `jumpTarget` may lie in another file (cross-file reference). Pass number is shown in labels as `×n` above 1.
- **Derivation for playing order** (`core/`, unchanged algorithm): right side of system k = gap k; left side of system k = gap k−1. A jump may start on the right side of the last system and target the left side of the first system.
- At most one `stop` per system; `stop` and `slideBreak` are not allowed on the last system; at most one `start` per file (the last one set wins); several `bookmark`s and several `jumpStart`s per system are allowed (earliest created wins on identical pass numbers, V1 rule PLY-006).
- **Start mark:** the playing order starts at the system of the `start` mark; systems before it are not played. Without a start mark it starts at the first system (V1).
- **Labels:** automatic label `<filename>:<page>:<system on page>`; the filename is omitted for marks of the same file. Jump: `start -> target`, `×n` when n > 1. An optional user text follows the automatic part.
- **Cross-file reference:** `{ file: <file name>, page, system }`; the file name is the only identity (D-1); stored in the file where the jump was created. Resolution (finding the file) is M6.
- **Deletion rules (D-24):** deleting a system deletes the marks stored on it (both sides); marks on neighbors stay. A page rerun keeps the marks of that page only if its system count is unchanged, otherwise the marks of that page are deleted. A reference to a vanished system is *unresolved* and is kept.

## Core part (first, `strong` model)

1. `docs/contracts/core/` gets compile-checked stubs and verified fixtures for: `marks.ts` (types, `addMark`, `removeMarksOfSystem`, `rerunPage`), `labels.ts` (`formatLabel`), `playing-order` changes (start mark, derivation), `migrate-v1.ts` (junction form → system form: origin gap k → right side of system k; target gap k → left side of system k+1; break and stop gap k → right side of system k).
2. Fixtures (table-driven, plain data): at least 25 cases for marks (conflicts, last system, first system, duplicate stop, start replacement), 15 for labels (same file, cross-file, page/system numbering across pages, ×n, user text), 12 for deletion/rerun rules, 20 for migration (V1 files from the real corpus's marks and hand-made edge cases: jump from gap N, target at gap 0, several jumps from one gap, break and stop at the same gap), 15 for playing order with a start mark. Fixtures of the V1 playing-order cases stay and are rerun against the derived model.
3. **Independent re-derivation:** a second pass (fresh session or explicit second read) re-derives the 10 hardest cases from this text without looking at the code; disagreements go to `docs/questions.md`.

## Steps (the owner commits after each)

### S1 — Contracts and red tests
Copy contracts and fixtures into `src/app/core/`, write specs with requirement IDs in test names, red.

### S2 — `core/` implementation and metadata schema
1. Implement `marks`, `labels`, playing-order changes; keep `junctions.ts`/`playing-order.ts` public behavior for fixtures that still apply.
2. `core/metadata.ts`: new `schemaVersion` (`T:saving.schemaVersion`), schema for marks on systems, start mark, bookmarks, user text, cross-file references; **read** migrates V1 data (SAV-003); an unknown newer version is ignored and never overwritten; existing files keep opening. The write path writes the new schema only.
3. Round-trip property test (seeded): random mark edits → serialize → parse → equal; V1 file → migrate → serialize → parse → equal derived playing order.

### S3 — State and callers
1. Adapt the stores that call the old marks API (`state/`: marks, playing order) to the new model without changing UI behavior; the organization UI still offers the V1 chips and maps them to system sides (right side for jump start/break/stop, left side for target). This keeps V1 flows working until M10.
2. Existing tests that assert the V1 junction model or PLY-002 (start at junction 0) are **explicitly allowed to change** where the new model supersedes them. List every changed test in the report with the reason. Any other failing existing test is a bug in the new code.

## Do not

- Do not build UI, tools or labels on screen (M10).
- Do not resolve cross-file references against real files (M6).
- Do not drop V1 reading support or change existing files on open without a user change.
- Do not add dependencies.
